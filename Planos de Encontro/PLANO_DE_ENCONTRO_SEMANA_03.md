## 2. Relação com o Cronograma

Segundo o `CRONOGRAMA.md`, a Semana 3 é a primeira semana de **Gate formal** do semestre: **Entrada em Produção Inicial**. A equipe só avança para a implementação (Semana 4) se tiver backlog priorizado, ferramenta de gestão em uso, repositório Git ativo e fluxo de build compreendido. Sem esses itens, o próprio encontro da Semana 4 é redirecionado para concluir a organização, em vez de iniciar a implementação — ou seja, este gate condiciona diretamente o ritmo da unidade seguinte.

**Entregáveis previstos para esta semana (Cronograma):**
- Projeto configurado na ferramenta de gestão.
- Repositório Git ativo.
- Primeira build vazia ou mínima gerada.

**Preparação exigida para a Semana 4:** primeiras tarefas do backlog prontas para implementação.

## 6. Estrutura do Encontro (2h15)

### Abertura (10 min)
Apresentação do encontro como Gate formal: explicar os critérios de aprovação para avançar à Produção Inicial e o que acontece caso uma equipe não os atenda.

### Checkpoints por equipe (35 min)
Cada equipe apresenta:
- ferramenta de gestão configurada;
- estado do repositório Git;
- fluxo de build proposto.

### Configuração assistida (40 min)
Suporte direto às equipes que ainda não finalizaram a configuração da ferramenta de gestão, do repositório ou do fluxo de build. Equipes já organizadas avançam para revisão fina do backlog priorizado.

### Verificação do Gate (35 min)
Avaliação individual por equipe, contra os critérios do Gate de Entrada em Produção Inicial. Registro formal de aprovação ou de pendências.

### Planejamento (10 min)
Cada equipe define as primeiras tarefas do backlog a implementar na Semana 4, condicionadas à aprovação (ou pendências) do Gate.

### Encerramento (5 min)
Síntese do status do Gate por equipe e reforço da meta da Semana 4.

*Os tempos podem ser ajustados conforme o número de equipes e o volume de suporte técnico necessário.*

## 10. Problemas Esperados

- Ferramenta de gestão escolhida, mas ainda não populada com o backlog real.
- Repositório Git criado sem estrutura clara ou sem primeiro commit relevante.
- Fluxo de build não testado ou desconhecido por parte da equipe.
- Dificuldade técnica na configuração de controle de versão.
- Equipe tratando esta semana como burocrática, sem perceber sua relevância para o ritmo da produção.

---

## 11. Estratégias de Intervenção

| Problema | Ação recomendada |
|---|---|
| Ferramenta de gestão vazia ou desatualizada | Usar parte do tempo de configuração assistida para migrar o backlog priorizado diretamente para a ferramenta, com a equipe. |
| Repositório sem estrutura clara | Orientar a organização mínima de pastas e o primeiro commit estruturado durante o próprio encontro. |
| Fluxo de build desconhecido | Solicitar que a equipe gere uma build simples ao vivo, com suporte do professor, para garantir compreensão prática do processo. |
| Dificuldade técnica com Git | Priorizar o suporte individual a essa equipe durante a configuração assistida, mesmo que reduza o tempo de mentoria de outras equipes já organizadas. |
| Semana tratada como burocrática | Reforçar, na abertura e no checkpoint, que ferramenta de gestão, Git e build são a infraestrutura que sustenta todas as entregas seguintes do semestre. |

## 13. Mini-Aula (Opcional)

**Tema sugerido:** "Fluxo básico de build e versionamento em equipe" (até 15 min).

Conteúdo sugerido: boas práticas mínimas de organização de repositório Git em equipe (branches, commits, .gitignore); o papel de uma build frequente como ferramenta de acompanhamento de produção, não apenas como entregável técnico.

Aplicável apenas se várias equipes demonstrarem dificuldade real com o fluxo de build ou versionamento — caso contrário, priorizar a configuração assistida individual.
